Wireshark Network Traffic Analysis

Overview

This project documents a hands-on network traffic analysis lab using Wireshark.

The lab builds on concepts learned through the TryHackMe Cyber Security 101 — Wireshark module. The TryHackMe material provided the foundation for understanding packet capture, protocol analysis, display filters, TCP communication, and packet inspection.

I applied those concepts in my own isolated VirtualBox lab using Kali Linux and Metasploitable 2. The traffic analyzed, screenshots, observations, and findings in this repository were produced during my own practical exercises.

TryHackMe — Cyber Security 101 — Wireshark

Methodology

1. Network Interface Identification

The Kali network interfaces were examined to identify the interface used by the isolated lab network.

The lab interface was:

eth1
192.168.56.104

Wireshark was then configured to capture traffic on "eth1".

---

2. Live Packet Capture

Wireshark was used to capture live traffic from the Kali lab interface.

This demonstrated the importance of selecting the correct network interface before beginning packet analysis.

---

3. ICMP Traffic Analysis

ICMP traffic was generated by sending ping requests to the Metasploitable target:

ping -c 4 192.168.56.105

The following Wireshark display filter was used:

icmp

The capture showed ICMP Echo Requests and Echo Replies between Kali and Metasploitable.

Security relevance: ICMP can be useful during network discovery and connectivity testing.

---

4. TCP Three-Way Handshake

An FTP connection was initiated from Kali to the Metasploitable FTP service:

ftp 192.168.56.105

The resulting TCP traffic was analyzed in Wireshark.

The TCP connection establishment demonstrated the three-way handshake:

SYN
SYN/ACK
ACK

This provided practical experience with how TCP establishes a connection before application data is exchanged.

---

5. Following a TCP Stream

A TCP packet belonging to the FTP connection was selected and the Follow → TCP Stream feature was used.

This reconstructed the communication between the FTP client and server.

The FTP server banner and authentication exchange were visible in the reconstructed conversation.

The exercise demonstrated an important security issue: traditional FTP does not encrypt its control traffic, meaning information transmitted through the connection can potentially be exposed to someone capable of capturing the traffic.

The password was redacted from the GitHub evidence.

---

6. DNS Traffic Analysis

DNS traffic was generated using:

nslookup google.com

The Wireshark display filter:

dns

was used to identify the DNS query and response.

During the exercise, it was also observed that the DNS traffic was traveling through the interface associated with the Internet/NAT connection rather than the isolated "eth1" lab interface.

This reinforced the importance of selecting the correct network interface when performing packet capture.

---

7. HTTP Traffic Analysis

HTTP traffic was generated by requesting the Metasploitable web server:

curl http://192.168.56.105

The following Wireshark display filter was used:

http

The HTTP request and server response were then examined.

The TCP stream was followed to view the HTTP conversation.

This demonstrated how unencrypted HTTP traffic can expose application-layer information to someone capable of capturing the traffic.

---

8. Filtering Traffic by IP Address

The following display filter was used:

ip.addr == 192.168.56.105

This isolated traffic involving the Metasploitable target.

Filtering by IP address is useful when a packet capture contains communication involving multiple hosts.

---

9. Filtering Traffic by TCP Port

The following display filter was used:

tcp.port == 21

This isolated TCP traffic associated with the FTP service.

Filtering by port allows specific services to be identified and investigated within a packet capture.

---

10. Inspecting TCP Packet Details

An FTP packet was selected and the TCP section of the packet details pane was expanded.

The following types of information were examined:

- Source port
- Destination port
- Sequence number
- Acknowledgment number
- TCP flags

This provided a deeper understanding of the communication occurring between the client and server.

Key Findings

Correct Interface Selection

The lab demonstrated that packet capture depends on selecting the interface through which the traffic actually travels.

The isolated penetration-testing traffic was captured through "eth1", while DNS/Internet traffic was associated with another interface.

TCP Communication

The TCP three-way handshake provided practical evidence of how TCP establishes a connection using SYN, SYN/ACK, and ACK packets.

TCP Stream Reconstruction

Wireshark's Follow TCP Stream feature made it possible to reconstruct a network conversation instead of analyzing individual packets separately.

Plaintext FTP Authentication

The FTP exercise demonstrated that traditional FTP transmits authentication information without encryption.

This means credentials can potentially be exposed through packet capture.

HTTP Traffic

The HTTP exercise demonstrated that unencrypted HTTP traffic can expose application-layer information within a network capture.

Display Filters

Wireshark display filters made it possible to quickly isolate specific traffic based on:

- Protocol
- IP address
- TCP port

---

Security Considerations

This lab was performed in an authorized and isolated VirtualBox environment.

The raw ".pcapng" capture may contain authentication information from the intentionally vulnerable FTP service. For this reason, the raw packet capture should remain private and should not be uploaded to the public GitHub repository.

The GitHub evidence uses a redacted screenshot instead.
